[[upgrade-5]]
= Upgrading from Coherence Spring 4.x to 5.x
include::attributes.adoc[]

Coherence Spring 5.x moves the project to Spring Framework 7 and Spring Boot 4. It is a major-version upgrade because
the surrounding Spring, Jakarta EE, persistence, JSON, security, and test ecosystems also move to new major versions.
The Coherence Spring artifact names and configuration-property prefixes remain unchanged, but applications may need
dependency and source changes according to the features they use.

This guide covers Coherence Spring-specific work. Also review the
https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide[Spring Boot 4 migration guide]
and https://github.com/spring-projects/spring-framework/wiki/Spring-Framework-7.0-Release-Notes[Spring Framework 7 release notes]
for the complete upstream changes.

The Java baseline does not change: Coherence Spring tests and supports Java 17 and Java 21. Coherence Spring 5.x
continues to use the `jakarta.*` namespace, but its Jakarta EE baseline advances from 10 to 11. Applications using
Servlet, Persistence, Validation, or other Jakarta APIs must use EE 11-compatible providers.

The Hibernate row is the project's explicit selection, not Spring Boot's managed default. See
xref:upgrade-5.adoc#upgrade-5-hibernate[Hibernate version selection] for the combinations used by the tests and samples.
Commercial Coherence compatibility has not been established for either line. Coherence 15.1.1.0.0's move to Jakarta
EE 9.1 does not by itself qualify a Spring 6 or Spring 7 application; see the repository README's compatibility note.

IMPORTANT: Upgrade a Spring Boot application to the latest 3.5.x maintenance release and remove use of APIs deprecated
in Boot 3 before moving to Boot 4, as recommended by the Spring Boot migration guide.

[[upgrade-5-sequence]]
== Recommended migration sequence

. On Coherence Spring 4.x, first move to its current Spring Boot 3.5 and Spring Framework 6.2 baseline and resolve all
  deprecation warnings that affect application code.
. Update the Spring Boot parent or BOM, Coherence Spring artifacts, and the explicitly declared Coherence CE dependency
  together. Do not mix Coherence Spring 4.x and 5.x modules in one application.
. Replace feature-specific integrations: Boot metrics and session modules, the Resilience4j Boot adapter, and the
  Coherence Hibernate adapter where applicable.
. Compile application and test source, then address the package and SPI changes listed below.
. Start the packaged application and exercise each enabled integration on the supported Java versions. Compilation alone
  does not prove that Boot 4 optional auto-configuration is active.

[[upgrade-5-dependencies]]
== Update dependency management

Use one source of Spring dependency management. Spring Boot applications should normally use the Boot 4 parent or BOM
and should not independently override the versions of Spring Framework, Spring Data, Spring Session, or Spring Security.

.Spring Boot parent and Coherence Spring dependencies
[source,xml,subs="verbatim,quotes,attributes"]
----
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>{spring-boot-version}</version>
</parent>

<dependencies>
    <dependency>
        <groupId>com.oracle.coherence.spring</groupId>
        <artifactId>coherence-spring-boot-starter</artifactId>
        <version>{coherence-spring-version}</version>
    </dependency>
    <dependency>
        <groupId>com.oracle.coherence.ce</groupId>
        <artifactId>coherence</artifactId>
        <version>{coherence-version}</version>
    </dependency>
</dependencies>
----

Plain Spring Framework applications should align Spring dependencies with its BOM and update the Coherence Spring
module version without adding the Boot starter.

.Plain Spring Framework dependency management
[source,xml,subs="verbatim,quotes,attributes"]
----
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-framework-bom</artifactId>
            <version>{spring-framework-version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>

<dependencies>
    <dependency>
        <groupId>com.oracle.coherence.spring</groupId>
        <artifactId>coherence-spring-core</artifactId>
        <version>{coherence-spring-version}</version>
    </dependency>
    <dependency>
        <groupId>com.oracle.coherence.ce</groupId>
        <artifactId>coherence</artifactId>
        <version>{coherence-version}</version>
    </dependency>
</dependencies>
----

Review exclusions and direct dependencies that compensated for Boot 3's larger modules. Boot 4 uses smaller,
feature-specific modules. Prefer Boot starters rather than depending directly on Boot's auto-configuration modules.
In particular, direct Boot integrations may now require `spring-boot-cache`, `spring-boot-session`,
`spring-boot-web-server`, or `spring-boot-micrometer-metrics` instead of relying on a larger Boot 3 module to provide
their classes transitively. The Coherence Spring starter supplies its required session module; metrics remain an
application-level choice.

[[upgrade-5-behavior]]
== Review feature-specific changes

[[upgrade-5-metrics]]
=== Metrics

Boot 4 moved registry auto-configuration out of `spring-boot-actuator-autoconfigure` and into
`spring-boot-micrometer-metrics`. Under Coherence Spring 4.x, adding `coherence-micrometer` could be sufficient to
activate a Boot-created registry. Under 5.x, the Coherence starter and `coherence-micrometer` still allow the application
to start, but no registry is created automatically and Coherence metrics are not bound.

Choose one of the following:

* Add `spring-boot-starter-actuator` if the application uses Actuator.
* Add `spring-boot-starter-micrometer-metrics` for Boot-managed metrics without Actuator.
* Supply an application-owned `MeterRegistry` bean.

See xref:spring-boot.adoc#spring-boot-metrics[Coherence Metrics] for complete Maven and Gradle examples and meter-filter behavior.

[[upgrade-5-session]]
=== Spring Session

Boot 4 moved session auto-configuration into `spring-boot-session`. Coherence Spring 5.x makes that module and
`coherence-spring-session` optional dependencies of the general `coherence-spring-boot-starter`. Applications using
only the general starter no longer receive Spring Session through it. The standalone session library remains
independent of Spring Boot.

Replace the previous two-artifact Boot session recipe:

[source,xml]
----
<dependency>
    <groupId>com.oracle.coherence.spring</groupId>
    <artifactId>coherence-spring-boot-starter</artifactId>
    <version>${previous-coherence-spring.version}</version>
</dependency>
<dependency>
    <groupId>com.oracle.coherence.spring</groupId>
    <artifactId>coherence-spring-session</artifactId>
    <version>${previous-coherence-spring.version}</version>
</dependency>
----

with the dedicated starter. Retain an explicit Coherence runtime and the application's servlet web dependencies;
the following assumes the Boot parent or BOM manages Boot versions:

.Boot servlet session dependencies for 5.x
====
.Maven
[source,xml,subs="verbatim,quotes,attributes",role="primary"]
----
<dependencies>
    <dependency>
        <groupId>com.oracle.coherence.spring</groupId>
        <artifactId>coherence-spring-session-boot-starter</artifactId>
        <version>{coherence-spring-version}</version>
    </dependency>
    <dependency>
        <groupId>com.oracle.coherence.ce</groupId>
        <artifactId>coherence</artifactId>
        <version>{coherence-version}</version>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-webmvc</artifactId>
    </dependency>
</dependencies>
----

.Gradle
[source,groovy,subs="verbatim,quotes,attributes",role="secondary"]
----
dependencies {
    implementation("com.oracle.coherence.spring:coherence-spring-session-boot-starter:{coherence-spring-version}")
    implementation("com.oracle.coherence.ce:coherence:{coherence-version}")
    implementation("org.springframework.boot:spring-boot-starter-webmvc")
}
----
====

The supported manual alternative is to declare all three integration artifacts instead of the new starter,
alongside the same Coherence and servlet prerequisites:

.Manual Boot session integration
====
.Maven
[source,xml,subs="verbatim,quotes,attributes",role="primary"]
----
<dependency>
    <groupId>com.oracle.coherence.spring</groupId>
    <artifactId>coherence-spring-boot-starter</artifactId>
    <version>{coherence-spring-version}</version>

    <artifactId>coherence-spring-session</artifactId>
    <version>{coherence-spring-version}</version>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-session</artifactId>
</dependency>
----

.Gradle
[source,groovy,subs="verbatim,quotes,attributes",role="secondary"]
----
dependencies {
    implementation("com.oracle.coherence.spring:coherence-spring-boot-starter:{coherence-spring-version}")
    implementation("com.oracle.coherence.spring:coherence-spring-session:{coherence-spring-version}")
    implementation("org.springframework.boot:spring-boot-session")
}
----
====

The old general-starter plus session-library combination alone no longer guarantees Boot HTTP-session activation.
It can start successfully without a Coherence session repository or HTTP filter. Setting
`coherence.spring.session.enabled=true` does not supply missing dependencies. After migration, verify the actual
`CoherenceIndexedSessionRepository` and `springSessionRepositoryFilter`, and exercise successive HTTP requests
using the same cookie with state stored in Coherence. Successful startup alone is insufficient.

Automatic integration supports servlet web applications, including Boot WARs; it does not provide reactive
WebSession support or enable HTTP sessions in a non-web application. Standalone Spring applications and storage
nodes can keep the session library without adding the new starter. See
xref:spring-boot.adoc#spring-boot-sessions[Spring Boot Session Support] and
xref:spring-session.adoc#spring-session-introduction[standalone configuration and storage dependencies].

Coherence session timeouts use Boot's `SessionTimeout` provider, available since Boot 4.0.1. For embedded servlet
applications, `spring.session.timeout` takes precedence over `server.servlet.session.timeout`. For WAR deployments
in an external servlet container, set `spring.session.timeout`; the server property is not a fallback. If no session
timeout is configured for a WAR deployment, the repository retains its default of 30 minutes. A `ServerProperties`
bean is not required for WAR session auto-configuration.

The existing back-off controls remain valid:

* Set `coherence.spring.session.enabled=false` to disable Coherence Spring Session auto-configuration.
* Define `spring.session.store-type` to opt out of Coherence's auto-configuration. Any value, including `none` or
  an empty value, disables it; this does not install or configure another store.
* Supply an application-owned `SessionRepository`. Coherence backs off; the application owns the repository
  and HTTP-session enabling. A bare repository bean does not create the HTTP filter. For a supplied repository,
  configure that explicitly, for example with `@EnableSpringHttpSession`.

If the application excludes starter dependencies or assembles Boot modules directly, verify that all three
integration artifacts and their required servlet/Session classes are present at runtime.

==== POF registrations

Existing applications using POF for sessions must extend their application-owned POF configuration for the operations
and authentication payloads they use:

* Register `com.oracle.coherence.spring.session.SessionResetEntryProcessor` when calling
  `CoherenceIndexedSessionRepository.resetMaxInactiveIntervalForActiveSessions()`. The method sends this processor to
  reset active sessions' inactivity intervals and cache expiry, independently of `use-entry-processor` /
  `useEntryProcessor`. Setting that option to `false` changes ordinary session updates; it does not avoid this registration.
* Register `org.springframework.security.core.authority.FactorGrantedAuthority` with
  `com.oracle.coherence.spring.session.serialization.pof.FactorGrantedAuthorityPofSerializer` when authentication graphs
  contain Spring Security 7 factor authorities. Without this mapping, saving or transporting such a graph with POF fails;
  this can affect login and subsequent session access. The serializer preserves both the authority and its issuance time.

See xref:spring-session.adoc#spring-session-pof[POF Serialization] for the complete configuration and operation table.
The example IDs `4001` (reset processor) and `3003` (factor authority) are illustrative, not reserved. Select unused IDs
and preserve all existing type-ID mappings while stored or persisted data depends on them. Deploy compatible mappings,
registered classes and serializer implementations to every application client and Coherence server that serializes,
deserializes or executes the affected objects. POF registration does not deploy those classes to remote endpoints.
Applications using Java serialization do not need these POF registrations, but receiving endpoints still need compatible
classes for their session graphs and repository operations.

==== Serialization compatibility and cut-over

Mixed Coherence Spring 4.x/5.x access to a session cache has not been qualified. Compatibility depends on the serializer,
the actual session attribute and authentication graph, and the classes and registrations available at each endpoint.
One concrete incompatibility is a 5.x authentication graph containing `FactorGrantedAuthority`: a stock 4.x application
using Spring Security 6 lacks that class and, for POF, its mapping and serializer. It cannot read that graph.

The 5.x `AuthenticationPofSerializer`, specific to `UsernamePasswordAuthenticationToken`, has regression coverage for
reading the legacy POF token format with uniform `SimpleGrantedAuthority` values and no authentication-state field.
Such legacy data retains its historical authenticated state because the old format did not record that state.
This demonstrates new-reader support for that legacy format; it does not establish old-reader compatibility with new
data, compatibility for arbitrary session graphs, or a safe mixed-version rolling upgrade or rollback.

Before reusing an existing session cache, validate the application's actual stored graphs, serializers and endpoint
registrations, and coordinate a cut-over that stops 4.x access before 5.x writes sessions. If compatibility cannot be
established, use an isolated session cache for 5.x (for example, set `coherence.spring.session.map-name` in Boot or the
`cache` attribute of `@EnableCoherenceHttpSession` to a different name) and require users to authenticate again. Ensure
requests and session cookies are routed to the intended deployment. Do not assume automatic data conversion or safe
rollback after 5.x has written sessions. Plan and validate rollback separately, including what happens to those sessions.

==== Hardened Coherence serialization

The project's default Coherence dependency remains 26.04; the hardened-serialization evidence described here concerns
Coherence 26.10 snapshots. On versions enforcing that policy, the Session JAR's permissions do
not cover arbitrary application-selected session attributes, principals or authentication details. Supply exact
application-owned `META-INF/coherence/security-config.xml` metadata for the required classes on the relevant receiving
endpoints. POF registrations and security permissions serve separate purposes; hardened POF deployments require both.

Follow xref:spring-session.adoc#spring-session-hardened-serialization[Hardened serialization and execution] for the
supported library graph and policy limits. The xref:spring-session.adoc#spring-session-sample[Spring Session samples]
provide separate app and server policies in the `spring-session-demo-app` and `spring-session-demo-server` modules at
`src/main/resources/META-INF/coherence/security-config.xml`. Each permits the chosen
`org.springframework.security.core.userdetails.User`, its `User$AuthorityComparator` (needed for Java serialization),
and `org.springframework.security.web.authentication.WebAuthenticationDetails`. These are examples for that concrete
graph; applications must review their own graph and supply any additional POF serializers and registrations it requires.

[[upgrade-5-resilience4j]]
=== Resilience4j

Replace the Boot 3 integration with its Boot 4 counterpart:

[source,xml,subs="verbatim,quotes,attributes"]
----
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot4</artifactId>
    <version>{resilience4j-version}</version>
</dependency>
----

Retaining `resilience4j-spring-boot3` can leave health integration inactive because it references Boot 3 health APIs.

[[upgrade-5-hibernate]]
=== Hibernate second-level cache

Applications using Coherence as Hibernate's second-level cache must move to the Hibernate 7 adapter.
https://github.com/coherence-community/coherence-hibernate/blob/v4.0.0/README.adoc[Coherence Hibernate 4.0.x supports Hibernate ORM 7.4.x only].
Declare both the adapter and a compatible ORM version; the adapter's Hibernate dependency is `provided` and does not
select the application's ORM version:

[source,xml,subs="verbatim,quotes,attributes"]
----
<dependency>
    <groupId>com.oracle.coherence.hibernate</groupId>
    <artifactId>coherence-hibernate-cache-7</artifactId>
    <version>{coherence-hibernate-version}</version>
</dependency>
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-core</artifactId>
    <version>{hibernate-version}</version>
</dependency>
----

Update the region factory class:

[source,yaml]
----
spring:
  jpa:
    properties:
      hibernate.cache.region.factory_class:
        com.oracle.coherence.hibernate.cache.v7.CoherenceRegionFactory
----

The Spring Boot {spring-boot-version} BOM manages `hibernate-core` at `7.2.24.Final`. This project combines that
managed default with explicit Hibernate ORM {hibernate-version} declarations as follows:

[cols="2,1,3",options="header"]
|===
|Usage |Hibernate ORM |Scope

|Boot starter tests
|{hibernate-version}
|Test dependency only; the general starter does not bring Hibernate into applications.

|`hibernate-cache-demo`
|{hibernate-version}
|Explicit runtime selection with `coherence-hibernate-cache-7` {coherence-hibernate-version}.

|`coherence-spring-demo-core` and `coherence-spring-demo-classic`
|{hibernate-version}
|Provided API dependency in core; explicit runtime dependency in the classic sample. These do not use the Hibernate cache adapter.

|`coherence-spring-demo-boot`, CacheStore, circuit-breaker and Cloud Config samples
|7.2.24.Final
|Boot-managed runtime selection, including `coherence-spring-demo-boot`; these do not use the Hibernate cache adapter.
|===

The project's `hibernate.version` property supplies explicit dependency declarations; it does not override the
Hibernate version inside an imported Boot BOM. Boot's managed 7.2 line is outside the Coherence Hibernate 4.0.x
adapter's supported 7.4 line. Applications enabling that adapter must select a compatible ORM version explicitly.

In local Java 17 and Java 21 reactor qualification, the starter tests had ORM {hibernate-version} on their test
classpath, the Hibernate cache sample started with that ORM version and adapter {coherence-hibernate-version},
and the CacheStore integration tests used Boot's managed ORM version. The Hibernate cache sample test verifies
application-context startup; it does not establish correctness of every second-level cache strategy or deployment combination.

Applications using Hibernate-specific query hints or APIs must also follow the Hibernate 7 migration guidance. For example, replace the old
`org.hibernate.annotations.QueryHints.CACHEABLE` constant with `org.hibernate.jpa.HibernateHints.HINT_CACHEABLE`.

[[upgrade-5-source]]
== Review application source and tests

Most Coherence Spring application code does not need source changes. Check the following when the corresponding
technology is used directly:

* **Jackson 3:** Boot 4's preferred JSON library uses `tools.jackson.*` coordinates and packages. Update imports such as
  `com.fasterxml.jackson.databind.ObjectMapper` to `tools.jackson.databind.ObjectMapper` when using Boot's managed mapper.
  Jackson annotations remain in `com.fasterxml.jackson.annotation`.
* **Spring Security 7:** use the lambda security DSL and `PathPatternRequestMatcher` where code previously used removed
  chained DSL methods or `AntPathRequestMatcher`.
* **Spring MVC parameter names:** compile with `-parameters` or give controller parameters explicit names. This is
  required when request binding or expressions such as `#id` depend on Java parameter names.
* **Spring Data extensions:** code extending Spring Data internals may need `org.springframework.data.core.TypeInformation`
  and the `ValueExpressionDelegate`-based repository-factory SPI. Ordinary Coherence repositories are adapted by 5.x.
* **Boot test modules:** Boot 4 modularized its test support. MVC tests may need `spring-boot-starter-webmvc-test`, and
  `@AutoConfigureMockMvc` is in `org.springframework.boot.webmvc.test.autoconfigure`.
* **Boot extension APIs:** custom Boot integrations may need `BootstrapRegistry` and `ConfigurableBootstrapContext` from
  `org.springframework.boot.bootstrap`, and must update imports for feature-specific auto-configuration packages.
* **JUnit:** the 5.x project baseline uses JUnit 6. Review custom extensions and test-engine dependencies even when
  ordinary Jupiter tests continue to compile unchanged.

Coherence Spring 5.x does not intentionally rename its `coherence.*` or `coherence.spring.*` configuration properties.
Cache names, session properties, repository enablement, ConfigData locations, and resource-injection annotations retain
their 4.x semantics unless an underlying Spring or Coherence feature imposes a change.

[[upgrade-5-validation]]
== Validate the upgraded application

Perform the migration on one supported JDK at a time and then verify both Java 17 and Java 21 if the application supports
both. At minimum:

. Generate and compare the resolved runtime dependency tree before and after the upgrade.
. Start the application with Boot's condition report enabled and confirm that the expected Coherence, cache, data,
  session, and metrics auto-configurations match.
. Exercise real cache access and any Coherence client or cluster topology used in production.
. Verify session creation, timeout, and back-off behavior when Spring Session is used.
. Verify meter registration and Actuator endpoints when metrics are used.
. Exercise HTTP parameter binding, Spring Security login/logout flows, serialization, persistence, and Hibernate
  second-level caching when those features are present.
. Run the complete application test and packaging lifecycle on every supported Java version.

Do not treat a successful compilation alone as migration acceptance. Boot's modular classpath and several relocated APIs
can allow startup while silently leaving an optional integration inactive.
